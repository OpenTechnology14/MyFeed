# Source and AI setup

Source collection is read-only. Optional manual Rocket.Chat/Mastodon-compatible publishing uses a separately configured writing token and explicit review/Send. The API contacts providers; the browser never receives reading/writing passwords or keys. Public HTTPS endpoints are supported; private-network addresses and nonstandard ports are rejected. No live publishing is claimed.

The [generated data matrix](DATA_MATRIX.md) documents stored fields, provider-to-entry mappings, normalized-text bounds, data visibility, retention, filtering, and removal. Connection setup and integration restrictions remain here.

Connection creation stores configuration first and then performs a visible initial sync. Failure does not pretend the source is connected: it shows Needs attention, a sanitized source error, and an activity receipt. Refresh feed retries enabled sources. Pause retains entries and stops inclusion/sync. Remove deletes local source credentials and data without changing the remote account.

AI processes excerpts, not full source documents. The generation instructions treat source text as untrusted, prohibit source-embedded actions, and ask for numbered citations. No tools are provided. Output is rendered as plain text and saved as a dated snapshot. Disconnecting AI removes its local key. Existing digest snapshots remain.

## Connection-first configuration and local editing

The [connection matrix](CONNECTION_MATRIX.md) separates source slots from local/processing capabilities. Local mention handles retain per-feed scope; AI retains workspace scope and compatible Settings links. External delivery still requires a separately selected provider/destination and explicit opt-in under PROP-026.

Local item edits (PROP-028) are presentation overlays in the owning source's Post log, with original/reset access and revision conflicts. They never grant provider writes or change source-derived filtering/mentions/AI. Use an exact model snapshot ID: a returned model identity that differs from the configured ID is rejected and retains an uncertain reservation. Moving aliases may therefore be rejected. Manual AI performs no provider call before review/confirmation; price bounds depend on user-verified rates. Input token counting follows the [OpenAI token-counting API](https://developers.openai.com/api/docs/guides/token-counting); review rates against [official pricing](https://developers.openai.com/api/docs/pricing) and the [per-run spending controller](https://developers.openai.com/cookbook/articles/per_run_spending_controller_responses_api).

Live public reads and mocked account checks are recorded separately in [IMPLEMENTATION.md](IMPLEMENTATION.md). Authenticated IMAP/Rocket.Chat and paid AI require configured user accounts and remain unverified. Read-only connection checks do not ingest; ordinary retention stays 300/source plus saved items even when older remote pages are fetched.

## API source configuration — 2026-10-08

API source setup: choose API source in Add connection, enter an HTTPS JSON endpoint and select the item array (blank path for a root array). Dot paths contain at most eight safe field segments; no expressions or scripts run. Stable ID is required; text fields map strings, optional tags map string arrays, image/link schemes are normalized. Missing dates use 1970-01-01 and malformed supplied dates fail. Configure next cursor path/query parameter only when the service supplies a bounded string cursor. At most 100 items/page and three pages/collection; a remaining cursor is available through Load older source items. Secrets belong in the encrypted credential field, never in the URL; credential-bearing redirects cannot cross origins. Repair retains blank credentials but API configuration changes require explicit reset. No generic OAuth, inbound webhook, outgoing calls or proprietary AI-service compatibility is inferred.

## Manual posting — implemented locally 2026-10-08

Implemented [PROP-033 composer/write setup](PROPOSAL_WORK_QUEUE.md#prop-033), [PROP-034 Rocket.Chat sends](PROPOSAL_WORK_QUEUE.md#prop-034), and [PROP-035 Mastodon-compatible publishing](PROPOSAL_WORK_QUEUE.md#prop-035). Open the owning connection → Configure writing account, explicitly enable manual posting and enter a separate writing credential. Blank tokens preserve only an already saved writing token, never fall back to a read/platform key. Check writing account performs read-only identity/destination/limit checks; it does not prove write permission. Save local draft → Review send → Send reviewed message. No live provider message was sent during implementation.

Rocket.Chat setup needs the writing user's ID/token and a joined ordinary public channel. Checks use `me` and `channels.info`; read-only, broadcast, archived, encrypted and non-public rooms are excluded. The local text/warning budget is capped conservatively at 2000 Unicode code points; server restrictions still apply. Replies are selected from this connection's collected items and resolve to a verified root in the configured room. One client message ID accompanies each single-channel send; alias/impersonation and URL preview fields are not enabled.

Mastodon-compatible setup needs a token with `write:statuses` plus `profile`/`read:accounts` for verification, and v2 instance metadata support. The conservative local body+warning limit uses instance `max_characters`, capped at 5000; server counting/URL conventions and permissions remain authoritative. Audience is explicitly unlisted/public/followers-only; language and warning are optional. Reply parents must have a valid local-instance collected status ID and are rechecked as accessible public/unlisted before transmission. Direct/private-parent replies, media, scheduling, boosts and remote editing/deletion are outside initial scope.

Writing source slots do not multiply: capability attaches to an existing supported connection. Pausing blocks review/send; read-configuration repair disables writing and invalidates identity, requiring setup/check again. Local drafts are plaintext in the restricted-permission data store, capped at 50. Five-minute reviews bind exact draft version, writer/source versions, sender, destination/audience, reply and limits. A fresh read-only preflight precedes Send; identity/configuration changes stop it before submission. Posting redirects are blocked; no redirected write or automated retry occurs.

The ledger persists Sending before provider contact and keeps up to 100 receipts, pruning only old settled outcomes. Duplicate receipt tokens never resubmit. A definite provider rejection keeps the draft editable and requires save/new review; network/malformed/ambiguous acknowledgment locks it Unknown. Restart converts interrupted Sending to Unknown. Inspect attempt/client IDs and provider outcomes manually before another post. Source deletion removes drafts and both keys while preserving send metadata; an already transmitted request can still complete and update its existing receipt without recreating the source/items. Local draft deletion does not retract remote messages. Both reading/writing ciphertexts are excluded from summaries and validated in paired protected backups; credential-free content export can include draft text/receipt metadata.

AI generation remains separate. The digest-copy shortcut first checks current configuration, revision and eligible references on a bounded history page; unavailable/stale/filtered snapshots cannot be copied through it. Only explicit manual copy changes a draft, and only Send publishes. Publishing metadata is distinct from collected provider originals, which arrive through subsequent ordinary ingestion.

Official references checked 2026-10-08: [Rocket.Chat send](https://developer.rocket.chat/apidocs/send-message) supports one room, optional client message ID and thread root with user ID/auth token; [postMessage](https://developer.rocket.chat/apidocs/post-message) also supports posting/replies. Server policy and room/account permissions govern actual access. [Mastodon status publishing](https://docs.joinmastodon.org/methods/statuses/#post) requires user `write:statuses`, supports visibility/content-warning/language/reply fields, and retains idempotency keys for up to one hour. [OAuth scopes](https://docs.joinmastodon.org/api/oauth-scopes/) declare permission separately from public reading. These docs establish an API path, not compatibility with every server or a live-account round trip.

Initial posting scope is text/links and supported replies. Private/DM rooms, uploads, broader Fediverse implementations, schedules, remote editing/deletion and multi-account cross-posting need separately declared support. Future providers use PROP-020 with independent read/write requirements; generic API ingestion, YouTube/TikTok access proposals and alert delivery do not grant posting rights.

### Read-only unknown-send recovery

Unknown receipts expose **Check send outcome** through Connections. Endpoint contracts were checked against the official [Rocket.Chat Get Message](https://developer.rocket.chat/apidocs/get-message) and [Mastodon status/source documentation](https://docs.joinmastodon.org/methods/statuses/#source). Rocket.Chat uses the original client message ID and compares sender, room, body and thread. Mastodon asks for a candidate post ID from the configured instance and fetches its status and original source (which may require `read:statuses`). It compares the original sender, text, warning, audience, explicit language and reply, and restricts creation time to one minute before through ten minutes after the attempt. A matching candidate establishes that the post exists; Mastodon does not expose independent attribution to the original idempotency key. The receipt records this distinction as `provider-lookup` confirmation.

These checks only issue provider GET requests. They work when writing is disabled or the source is paused, provided the original connection and writing credentials remain available. Missing/mismatched results, insufficient permissions, legacy receipts without frozen identity evidence and source deletion leave uncertainty locked; they never authorize retry or imply failure. Local fixtures cover matches, mismatches, restart and deletion races; live provider lookup remains unverified.

### YouTube checkpoint review — 2026-10-09

Refresh begins at the current first playlist page, then resumes any pending catch-up within the three-page bound. The newest checkpoint advances only when that catch-up finishes; initial bounded collection keeps remaining old history for explicit Load older. Fetch/duration failures commit no checkpoint. This behavior was reviewed against [YouTube pagination](https://developers.google.com/youtube/v3/guides/implementation/pagination) and tested with mocked pages; it is not live account proof. TikTok's [app review guidelines](https://developers.tiktok.com/docs/en/app-review-guidelines) were rechecked and still exclude private/personal-use apps, supporting the local-edition unsupported disposition.
