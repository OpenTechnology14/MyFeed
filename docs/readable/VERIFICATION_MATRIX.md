# Verification matrix

Baseline: 2026-10-04. Use this change-to-check mapping with the [full application audit](FULL_APPLICATION_AUDIT_MATRIX.md). Following a sibling project's verification structure, each row states both required proof and its limits. Another sibling project's path-audit approach supplies the UI/API/persistence/recovery/cleanup dimensions. Commands and boundaries below are specific to MyFeed.

The existing repository-wide code gate is `npm run verify` (type check/production build, local unit/API/mocked tests, generated doc synchronization). Stop the normal server before E2E: Playwright owns ports 3188/5188 and uses a named temporary directory plus a unique session marker. Global setup verifies the API's matching marker before any workflow; test-marked traffic is denied by a normal API, and production/default/symlinked stores cannot start in test mode. Check normal store/key fingerprints before/after browser runs. Restore the user preview afterward. The controlled negative test with an active normal server must fail before workflows and leave its store unchanged; it does not run destructive browser actions.

## Evidence classes and execution results

Manual browser testing uses `npm run test:manual`, the [manual workflow](MANUAL_TESTING_WORKFLOW.md), [generated interaction checklist](../agent-registries/CLICK_TREE_MANUAL_CHECKLIST.md), and [dated results](MANUAL_TEST_RESULTS.md). The real local API persists fictional Sample library content in a guarded temporary store; it is separate from mocked upstream and live account evidence. The launcher refuses occupied ports, verifies the proxy/API session marker, and checks normal store/key fingerprints at teardown.

| Evidence class            | Examples in this repository                                     | Claim allowed                                                                       |
| ------------------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Source inspection         | model, route/handler, component review                          | Code/contract exists; no runtime result inferred                                    |
| Local unit/API            | pipeline, presentation, alerts, API, preview tests              | Named assertions passed in isolated local conditions when a dated run is recorded   |
| Mocked upstream           | connectors.test.ts, ai.test.ts                                  | Request/normalization/race contract under supplied responses; no real account proof |
| Sample browser            | workspace.spec.ts, pages.spec.ts                                | Exercised UI paths against isolated fictional data                                  |
| Live provider             | Dated controlled public-source or authorized account round trip | Only the provider, account capability, environment, and path actually checked       |
| User arrangement approval | Explicit feedback for each of five page arrangements            | Accepted layout scope; no provider/API assurance                                    |

Execution statuses: **PASS**, **FAIL**, **BLOCKED** (name the missing fixture/dependency), **NOT RUN**, **NOT IMPLEMENTED**, and **EXPECTED DENY**. These are independent of product backlog statuses. Existing test files are evidence locations; only a recorded execution establishes a pass. Historical results stay dated in [IMPLEMENTATION.md](IMPLEMENTATION.md).

## Result record

Each completed change records date, source/build identifier if available, changed feature/click/connection/API/audit IDs, commands and exact outcomes, evidence class, skipped checks with reason, sanitized artifact locations, and fixture cleanup. Include unresolved risk relevant to the change. Do not record credentials, mailbox/post contents, or another application's data. Use the [proposal queue](PROPOSAL_WORK_QUEUE.md) for failures and missing scope rather than maintaining a competing task order here.

## Live account verification procedure

This procedure prepares PROP-010/011; it is **NOT RUN** until a test account is explicitly configured. Do not enter credentials into documentation or chat. Configure the account through Connections. Use a dedicated test mailbox/public channel with non-sensitive existing fixtures. Record counts, timestamps, provider version where known, local source/item identifiers and sanitized outcome categories; omit subjects, bodies, addresses and tokens from evidence. Reading checks never require enabling manual posting or submitting a test message.

| Stage                  | Email (PROP-010)                                                                                                         | Rocket.Chat (PROP-011)                                                                                               | Evidence to record                                                                                         |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Account readiness      | Explicit supported TLS IMAP account, mailbox and credential; establish baseline remote Seen flags in the provider client | Public HTTPS server, public channel ID and reading user/token with access; existing channel/thread fixtures          | Account-specific capability scope and unmet requirements, without account identifiers/secrets              |
| Initial collection     | Add source; inspect its health, Activity and Post log; compare existing fixture structure with the email reader          | Add source; inspect health/Activity/Post log; compare channel/root/reply identities and chronological conversation   | Dated success/error category, counts and source run ID; no content logs                                    |
| Repeat and local state | Save/read one local item, refresh twice, reload; compare stable identity/state and remote Seen baseline                  | Save/read one item, refresh twice, reload; compare stable channel/thread identity and local state                    | Duplicate count and local-state/remote-state result; failure blocks a live-proof claim                     |
| Filtering and history  | Link a test feed; apply a rule and confirm originals in source Post log; explicitly load older items                     | Exclude a known fixture message; verify it does not reappear as conversation context; explicitly load older messages | Eligible/history counts, checkpoint outcome and filter explanation; retained history is bounded            |
| Pause and repair       | Pause/refresh, resume; only on the dedicated account test bad credentials, visible failure and valid repair              | Pause/refresh, resume; only on dedicated source test permission failure and valid repair                             | Pause persistence, sanitized failure/recovery and checkpoint preservation                                  |
| Restart and cleanup    | Restart local app; recheck source/IDs/read/save and unchanged remote Seen flags                                          | Restart local app; recheck room/thread/IDs/read/save                                                                 | Restart result; remove only clearly identified disposable test source/feed after reviewing local data loss |

Oversized email fixtures, UIDVALIDITY changes, provider rate limits and in-flight deletion races remain mocked evidence unless actually exercised against a dedicated authorized environment. Never fabricate provider failure or mailbox changes in a real personal account to satisfy a checklist. A passing public feed, mock, or browser workflow does not satisfy these live-account criteria. Use the result record above and retain the existing proposal as pending if any required live step is unavailable.
