# T3-UI-01 — MyFeed T3 feed integration + inline decision-answer UI

**Status:** Scoping only. Registered as `WM-MYFEED-T3-UI-01-SCOPE` in an internal coordination
tracker. **Type:** Specification document. **No code changes accompany this document.**

**Depends on:** `T3-MCP-01` (a sibling internal coordination project) for the actual MCP/API
surface a MyFeed client would call. At the time of writing, `T3-MCP-01` is wall-blocked on that
project's side (until 5:20pm ET) and has no proposal doc or API shape committed yet there.

This document is written so MyFeed's own planning, UI decisions, and phase breakdown do **not**
depend on T3-MCP-01's eventual exact shape. Every integration point below is described as a
capability MyFeed needs ("fetch open Questions for this project," "post an answer for a Question
ID"), not as a specific transport, schema, or client library. When T3-MCP-01 lands, only the
integration-adapter layer (see "Integration boundary" below) should need to change.

---

## Goals

1. A MyFeed user (the owner) can see open T3 Questions relevant to MyFeed without leaving the
   app or opening the the internal coordination repo repo.
2. The owner can answer a Question inline, from a small fixed set of options (A/B/C/… style),
   without typing free text into a terminal or editing a markdown file by hand.
3. Once answered, the corresponding T3 row is marked resolved on the server side — the owner's
   answer is the single source of truth, not a chat message that an agent has to remember to go
   write down.
4. (Phase 3, stretch) The same view works across every T3-registered project the owner runs, not
   just MyFeed — but MyFeed's own phase 1/2 do not require this to ship first.

## Non-goals

- MyFeed does not become a general T3 editor. No creating/editing/deleting Questions, no backlog
  management, no PR review from inside MyFeed. Just: see Questions, answer Questions.
- MyFeed does not run or own any part of the T3 coordinator, standup, or hourly-close logic. It
  is a _client_ of whatever read/write surface T3-MCP-01 exposes.
- No change to MyFeed's existing product rules (feed/connection limits, Connections-first setup,
  AI opt-in boundaries) — this is additive, and if it needs a new feed-like surface it follows
  the same Connections-first pattern already in place for every other feature.

## Integration boundary (the part that stays stable regardless of T3-MCP-01's shape)

MyFeed needs exactly two capabilities from the T3 side, expressed as abstract operations:

```
listOpenQuestions(projectId) -> Question[]
answerQuestion(questionId, choice) -> { resolved: boolean }
```

Where `Question` is, at minimum: `{ id, projectId, prompt, options: string[], context, raisedAt }`.

Everything MyFeed builds (phase 1 and 2 below) is written against this shape. A dedicated
`server/t3-client.ts` adapter (not built in this scoping pass) is the only file that would need
to change once T3-MCP-01's real API/MCP surface exists — translating the real transport
(MCP tool calls, REST, or a GitHub-API read of the internal coordination repo markdown/JSON, whichever
T3-MCP-01 picks) into the two operations above. Everything above the adapter — the feed card UI,
the answer-inline flow, the dashboard — is built against the abstract shape and does not change.

Open decision gate **T3-UI-D01**: see [Decision gates](#decision-gates-summary) and its [reasoning](#reasoning-for-t3-ui-d01).

## Phase breakdown

### Phase 1 — read-only feed view of Questions

A new feed-like card (or a dedicated "T3 Questions" entry alongside Connections, following the
existing Connections-first setup pattern) that lists open Questions for MyFeed's own project,
read-only. Each Question shows its prompt, options, and context — no answering yet.

- Scope: `listOpenQuestions` only, rendered as cards.
- Storage: no new persistent state in MyFeed beyond what's needed to cache the last fetch (same
  atomic-file pattern as `server/store.ts`, a new bounded local cache, not a new database).
- Opt-in: following CLAUDE.md's Connections-first rule, this surface is off by default and the
  owner turns it on explicitly, same as every other connection/feature in the app.

Open decision gate **T3-UI-D02**: see [Decision gates](#decision-gates-summary) and its [reasoning](#reasoning-for-t3-ui-d02).

### Phase 2 — answer-inline UI

Builds on phase 1: each Question card gets its option buttons (A/B/C/…) wired to
`answerQuestion`. Confirming an answer is an explicit, reviewable action — matching the existing
review-before-send pattern already used for posting (PROP-033–035) and AI generation (PROP-029):
show exactly what will be submitted, require a confirm click, no auto-submit.

- Scope: `answerQuestion` call, with a confirmation step and a visible "answered" state on the
  card afterward (no polling-and-hope — the UI should reflect the adapter's return value directly,
  and treat an uncertain/interrupted answer send the same way PROP-026's alert outbox treats an
  uncertain delivery: don't assume success, don't auto-retry silently).
- Error states: network/API failure before send → nothing was submitted, say so plainly. Failure
  after send but before confirmation of receipt → surface as "unknown, check T3 directly," never
  silently retried.

Open decision gate **T3-UI-D03**: see [Decision gates](#decision-gates-summary) and its [reasoning](#reasoning-for-t3-ui-d03).

### Phase 3 — dashboard across projects (stretch, not required for phase 1/2)

A single view aggregating open Questions across every T3-registered project the owner runs (not
just MyFeed), likely surfaced from Settings or a dedicated dashboard page rather than the reader.

- Scope: `listOpenQuestions` called per project, rendered as one combined, project-labeled list.
- Explicitly out of scope for this pass: cross-project answer routing, since answering a
  non-MyFeed project's Question from inside MyFeed raises an authority question (should MyFeed
  be allowed to resolve, say, another project's Question?) that phase 1/2 don't need to settle.

Open decision gate **T3-UI-D04**: see [Decision gates](#decision-gates-summary) and its [reasoning](#reasoning-for-t3-ui-d04).

## Model routing recommendation

- **Drive model:** a general coding-capable model at normal effort is sufficient for phase 1/2 —
  this is UI plumbing against an abstract two-operation interface, matching the complexity of
  existing feature work in this repo (e.g. the posting-panel or alert-outbox UI work). No need
  for a higher-effort/reasoning-heavy model unless T3-MCP-01's real shape turns out to need
  non-trivial translation logic in the adapter.
- **Review model:** the existing `code-review` pattern already used in this repo (effort chosen
  per change size) is sufficient; no specialized review model needed. Given this touches a new
  external-trust boundary (the T3/the internal coordination repo side of the adapter is operator content,
  not user input, but still an external system), a security-focused review pass on the adapter
  layer specifically (once built) is worth calling out explicitly rather than assuming the
  default review catches it.

## What this scoping pass did not do

No code was written. No T3-MCP-01 API was called or inspected (it doesn't exist yet as a
committed shape). Phase 1 cannot start in earnest until **T3-UI-D01** is answered — if the
owner wants a stub adapter now, phase 1 UI work can begin immediately in parallel with
T3-MCP-01; if not, phase 1 implementation waits.

## Reasoning for each decision gate

Every gate above is written in two tiers: its row holds only the question and a suggested answer of one to three words, and the full reasoning for each is here, in the shape of the [decision gates](https://github.com/OpenTechnology14/AgentWorkflows/blob/main/workflows/DECISIONS.md) policy. Where the proposal records no recommendation, the suggestion is the author's and the context says so.

### Reasoning for T3-UI-D01

- **Context:** MyFeed's T3 integration is written against two abstract operations, listOpenQuestions and answerQuestion, behind one adapter file (server/t3-client.ts, not built yet). The real transport comes from T3-MCP-01, a sibling internal coordination project that is wall-blocked and has no proposal document or API shape committed yet. The question is whether the adapter's first implementation is a stub returning canned or local sample questions, so UI work is not blocked, or whether UI work waits for any working endpoint, even a rough one. The proposal records no recommendation, so the suggestion is the author's: a stub first. The gate blocks the start of Phase 1 implementation.
- **Prerequisites:** None — a stub needs only the abstract two-operation interface, which the proposal already fixes.

#### Option A: Stub first (Suggested)

- **What it is:** Build the adapter's first version as a stub that returns canned or local sample questions, so Phase 1 UI work starts now, in parallel with T3-MCP-01.
- **Unlocks:** Phase 1's read-only feed card can be built, run and reviewed without any T3 endpoint.
- **Blocks:** Nothing in the plan; the stub is replaced behind the same two operations when a real endpoint exists.
- **Risks:** A stub can drift from the real shape, so UI built on sample data may need small changes when the adapter is swapped; the proposal limits this by keeping the question shape minimal.
- **Effort:** Agent: a stub adapter and sample data. Unknown — the proposal does not size it.
- **Money:** None — no spend is named.
- **Incompatible with:** Waiting for an endpoint before any UI work.
- **Needs first:** None — the abstract interface is already fixed in the proposal.

#### Option B: Wait for endpoint

- **What it is:** Phase 1 UI work waits until T3-MCP-01 has any working endpoint, even a rough one.
- **Unlocks:** UI built against the real shape from the start.
- **Blocks:** Phase 1 implementation, which cannot start until then.
- **Risks:** Phase 1 can wait as long as T3-MCP-01 does, and that project has no committed API shape yet; how long is Unknown.
- **Effort:** None — nobody has any work to do now.
- **Money:** None — nothing is spent.
- **Incompatible with:** A stub adapter now.
- **Needs first:** A working T3-MCP-01 endpoint.

#### Trade-offs

| Axis                                  | A (Suggested)            | B                               |
| ------------------------------------- | ------------------------ | ------------------------------- |
| Phase 1 can start                     | Now                      | After T3-MCP-01 has an endpoint |
| Rework when the real endpoint arrives | Some, behind the adapter | None                            |
| Work now                              | A stub and sample data   | None                            |
| Can it be undone                      | Yes, swap the adapter    | Yes                             |

- **Downstream impact:**
  - **Changes:** A stub adapter and sample data are added to MyFeed's server code when Phase 1 starts; the real adapter replaces it later behind the same two operations. Under Wait for endpoint nothing changes.
  - **Unblocks:** The start of Phase 1 implementation.
- **Cost of deferring:** Phase 1 implementation stays blocked; the proposal says it cannot start in earnest until this is answered. The row records no default. Waiting costs as long as T3-MCP-01 stays unshipped.
- **Worst case:** The stub's sample data misleads the UI design. It shows up when the real adapter returns a different shape, and the way back is to adjust the card against the real operations.

### Reasoning for T3-UI-D02

- **Context:** Phase 1 adds a read-only card that lists open questions for MyFeed's own project. It could live inside the existing mixed reading timeline, with posts, articles and conversations, or on its own separate surface, like Settings or Connections, that never mixes with the reading feed. MyFeed's product rule of no content-type tabs in the reader argues for a separate surface; mixing risks forcing a content-type distinction into the reader that does not exist today. The feature is off by default and follows the existing Connections-first pattern. The gate blocks Phase 1 UI placement, and the suggestion follows the proposal's own lean.
- **Prerequisites:** None — the answer stands alone; the card is off by default and the owner turns it on explicitly.

#### Option A: Separate surface (Suggested)

- **What it is:** The T3 questions view is its own surface, like Settings or Connections, and never mixes with the reading feed.
- **Unlocks:** A reader that stays free of a content-type distinction, in line with the product rule of no content-type tabs.
- **Blocks:** Questions appearing among posts and articles.
- **Risks:** Questions are easier to miss than in the timeline, because the owner has to open the surface; low impact for a read-only list the owner turns on deliberately.
- **Effort:** Agent: a new settings-style surface. Unknown — the proposal does not size it.
- **Money:** None — no spend is named.
- **Incompatible with:** Placing the card in the mixed timeline.
- **Needs first:** The Connections-first opt-in, off by default.

#### Option B: Mixed timeline

- **What it is:** The card appears inside the existing reading timeline, among posts, articles and conversations.
- **Unlocks:** Questions seen where the owner already reads.
- **Blocks:** The rule that the reader has no content-type distinction.
- **Risks:** It forces a content-type distinction into the reader that does not exist today, which the product rule argues against.
- **Effort:** Agent: a new card type in the reader. Unknown — the proposal does not size it.
- **Money:** None — no spend is named.
- **Incompatible with:** The product rule of no content-type tabs in the reader.
- **Needs first:** A change to the reader's product rule.

#### Trade-offs

| Axis                             | A (Suggested)             | B                       |
| -------------------------------- | ------------------------- | ----------------------- |
| Reader stays one kind of content | Yes                       | No                      |
| Chance the owner sees a question | Lower, a separate surface | Higher, in the timeline |
| Fit with existing patterns       | Connections-first         | New to the reader       |
| Can it be undone                 | Yes, move the card        | Yes, move the card      |

- **Downstream impact:**
  - **Changes:** Phase 1's card is built as its own surface beside Settings and Connections. Under Mixed timeline the reader gains a new card type.
  - **Unblocks:** Phase 1 UI placement.
- **Cost of deferring:** Phase 1 UI placement stays blocked. The row records the proposal's lean (a separate surface) but no default is applied. Waiting costs when Phase 1 UI work starts.
- **Worst case:** The separate surface goes unvisited. It shows up as questions the owner does not see, and the way back is to add a pointer from the reader or move the card.

### Reasoning for T3-UI-D03

- **Context:** Phase 2 lets the owner answer a question with option buttons wired to answerQuestion, after an explicit confirm step. The open point is what resolved on the server side means: either MyFeed's adapter call itself flips the T3 row from open to resolved (MyFeed has write access to the T3 state), or MyFeed only records the owner's choice and a separate coordinator process resolves the row after reading it. The answer changes where the source of truth lives and how resolved is reported back to the UI. The proposal records no recommendation, so the suggestion is the author's: let the coordinator resolve.
- **Prerequisites:** None for the answer; Phase 2 itself needs Phase 1 and a working T3-MCP-01 surface.

#### Option A: Coordinator resolves (Suggested)

- **What it is:** MyFeed records the owner's choice through the adapter, and the T3-side coordinator resolves the row after reading it; the card shows the answer as recorded, then resolved when the coordinator reports it.
- **Unlocks:** MyFeed needs no write authority over T3 state, which keeps its trust boundary small.
- **Blocks:** An instant resolved state in the UI.
- **Risks:** There is a delay between answering and resolved, and the UI must show both states honestly; an uncertain send is shown as unknown and never silently retried.
- **Effort:** Agent: the answer call and a recorded-then-resolved card state. Unknown — the proposal does not size it.
- **Money:** None — no spend is named.
- **Incompatible with:** MyFeed resolving rows itself.
- **Needs first:** A coordinator process on the T3 side that reads recorded answers.

#### Option B: MyFeed resolves

- **What it is:** MyFeed's answerQuestion call itself flips the T3 row to resolved, so the card reports resolved at once.
- **Unlocks:** One step: the owner's answer is the single source of truth immediately.
- **Blocks:** A small trust boundary, since MyFeed would hold write access to T3 state.
- **Risks:** A bug or a compromised client could resolve rows wrongly; the proposal flags the adapter as a new external-trust boundary that needs its own security review.
- **Effort:** Agent: the answer call and its security review. Unknown — the proposal does not size it.
- **Money:** None — no spend is named.
- **Incompatible with:** A coordinator-side resolve.
- **Needs first:** Write access to T3 state from MyFeed, which T3-MCP-01 would have to offer.

#### Trade-offs

| Axis                           | A (Suggested)                 | B                                           |
| ------------------------------ | ----------------------------- | ------------------------------------------- |
| Authority MyFeed holds         | Record only                   | Write access to T3 state                    |
| Resolved shown in the card     | After the coordinator reports | At once                                     |
| Security review of the adapter | Lighter                       | Heavier                                     |
| Can it be undone               | Yes                           | Yes, but a wrong resolve needs a manual fix |

- **Downstream impact:**
  - **Changes:** Phase 2's card has a recorded state and a resolved state, and the adapter exposes no resolve call. Under MyFeed resolves the adapter calls resolve and holds write access.
  - **Unblocks:** Phase 2's resolved semantics and its error-state design.
- **Cost of deferring:** Phase 2's resolved semantics and error-state design stay blocked, and Phase 1 is not affected. The row records no default. Waiting costs when Phase 2 starts.
- **Worst case:** Coordinator resolves proves too slow for the owner. It shows up as answers that stay recorded for a long time, and the way back is to ask T3-MCP-01 to let MyFeed resolve under the review described above.

### Reasoning for T3-UI-D04

- **Context:** Phase 3, a stretch, would show open questions across every project the owner runs in one project-labelled list. Answering another project's question from inside MyFeed raises an authority question, whether MyFeed should be allowed to resolve another project's question, that Phases 1 and 2 do not need to settle; the proposal keeps cross-project answer routing out of scope for now. The question is whether Phase 3 only reads other projects' questions and defers cross-project answering to a later proposal, or answers across projects from its first day. The suggestion follows the proposal's own lean. The gate does not block Phases 1 and 2.
- **Prerequisites:** None for the answer; Phase 3 itself needs Phases 1 and 2.

#### Option A: Read only (Suggested)

- **What it is:** Phase 3 only reads other projects' questions; answering across projects is left to a later, separately scoped proposal.
- **Unlocks:** A combined view with no authority question to settle.
- **Blocks:** Answering another project's question from MyFeed.
- **Risks:** The owner must go to each project to answer; low impact for a stretch phase.
- **Effort:** Agent: a per-project read and one combined list. Unknown — the proposal does not size it.
- **Money:** None — no spend is named.
- **Incompatible with:** Cross-project answering in Phase 3.
- **Needs first:** None — Phase 3 follows Phases 1 and 2.

#### Option B: Answer too

- **What it is:** Phase 3 also answers other projects' questions from inside MyFeed.
- **Unlocks:** One place to answer everything.
- **Blocks:** A phase 3 free of the authority question.
- **Risks:** MyFeed would be allowed to resolve another project's question, which raises the authority question and widens the trust boundary.
- **Effort:** Agent: cross-project answer routing and its review. Unknown — the proposal does not size it.
- **Money:** None — no spend is named.
- **Incompatible with:** A read-only Phase 3.
- **Needs first:** An answer to the authority question, and T3-MCP-01 support for cross-project writes.

#### Trade-offs

| Axis                   | A (Suggested)            | B                |
| ---------------------- | ------------------------ | ---------------- |
| Authority question     | Avoided                  | Must be settled  |
| Owner effort to answer | Per project              | From one place   |
| Scope of Phase 3       | Smaller                  | Larger           |
| Can it be undone       | Yes, add answering later | Harder to narrow |

- **Downstream impact:**
  - **Changes:** Phase 3's scope is recorded as a read-only combined view. Under Answer too the scope adds cross-project answer routing.
  - **Unblocks:** Phase 3 scope, which is a stretch and does not block Phases 1 and 2.
- **Cost of deferring:** Only Phase 3 scope waits; Phases 1 and 2 proceed. The row records the proposal's lean (read only) but no default is applied. Waiting costs nothing until Phase 3 is planned.
- **Worst case:** Read only proves too limited for the owner. It shows up as a wish to answer from the dashboard, and the way back is the separate proposal for cross-project answering.
